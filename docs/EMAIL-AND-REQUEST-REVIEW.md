## Gmail settings to verify

In Supabase's custom SMTP settings, check:

| Setting | Value |
| --- | --- |
| SMTP host | `smtp.gmail.com` |
| Port | `465` for SSL, or `587` for STARTTLS |
| Username | The full sending Gmail address |
| Password | A Google App Password generated for this integration |
| Sender email | The authenticated Gmail address, or an authorized sending alias |

Enable 2-Step Verification on the sending Google account before creating an App Password. A normal Google account password is not suitable for this SMTP integration. Google revokes App Passwords when the main account password changes, so an old credential may need replacement. Store this password only in Supabase's SMTP settings.

Use Supabase **Authentication → Logs** to inspect the latest `/signup` or `/resend` attempt. SMTP authentication errors, connection/TLS errors, and sending-limit errors point to different fixes. If the request succeeds, check whether the account was already confirmed, then check the sending mailbox for bounce messages and the recipient's spam folder. Personal Gmail does not provide the same delivery-event dashboard as a dedicated transactional email provider.

## Why signup can succeed without a code arriving

`auth.signUp()` requests the first confirmation email. Visiting `/verify` does not send a second email. The page's Resend button calls `auth.resend({ type: 'signup' })`. Successful API responses confirm request acceptance, not inbox delivery. Supabase can also conceal whether an email is already registered by returning a generic signup response; confirmed accounts do not need another signup code.

Check these settings in the Supabase Dashboard:

1. **Authentication → Email / SMTP:** confirm the custom Gmail configuration is enabled and saved, using the settings above. If custom SMTP is disabled, the built-in provider restricts recipients to project team members and currently limits sending to two emails per hour. Never add normal app users to the Supabase organization to work around this restriction.
2. **Authentication → Email Templates → Confirm signup:** copy the contents of `supabase/templates/confirm-signup.html` into this template. This signup flow needs `{{ .Token }}`. Editing only the Magic Link template will not change signup emails. The local HTML file is a template to copy; it is not automatically deployed.
3. **Authentication → URL Configuration:** allow your actual app origin followed by `/auth/callback`, for example `http://localhost:5173/auth/callback` in development and your HTTPS production origin. This supports confirmation links and Google sign-in; numeric codes do not require clicking a link.
4. **Authentication → Users:** inspect the intended account's confirmation status. Already confirmed or Google users should log in with their existing method. Do not delete real accounts for testing.
5. **Authentication → Logs**, plus your email provider's delivery logs: inspect the signup/resend request at the time it happened. Look for `email_address_not_authorized`, `over_email_send_rate_limit`, SMTP authentication failures, bounced/suppressed recipients, or a successful send. Check spam, sender verification, and provider restrictions when Supabase accepted the request.
6. Keep email confirmation enabled. Do not disable it to bypass a delivery problem. Use a user-controlled test address for an end-to-end delivery test; no signup or resend emails were sent during this review.

SMTP credentials, private Auth logs, and the active email template are not accessible through the public app key. Actual inbox delivery remains unverified.

## Request and catch fixes

- Auth, database, and storage errors now share a formatter that handles both `Error` instances and plain Supabase error objects.
- Verification normalizes email addresses, validates empty/invalid inputs, requires a returned user and session, prevents concurrent submits, and provides a 60-second resend cooldown. The cooldown is a UI aid; the server's configured limits still apply and may be longer.
- Signup and resend use `/auth/callback` when an email contains a confirmation link. The verification screen does not falsely guarantee delivery and directs existing users back to login.
- Unconfirmed-email login errors provide a verification link. Missing profiles and failed permission lookups no longer silently look like ordinary user logins.
- Public signup/verification routes remain reachable when session validation fails. Protected routes fail closed and redirect to login with an explanation.
- Logout checks returned errors. List/detail fetches show plain-object errors and discard older overlapping responses. Invalid destination IDs are rejected before querying.
- Admin edit waits for nearby records before replacing the form, blocks overlapping edit/delete/save operations, checks authentication errors, and checks whether deletes affected a row. After a destination is created, retries reuse its ID if nearby-place synchronization fails. Partial-save and refresh errors are distinguished from a completely failed save.

## Remaining database work

Saving a destination and its nearby places still uses separate requests. Deleting old nearby rows and then failing to insert replacements can leave missing rows. The screen preserves the draft and explains how to retry, but a database transaction/RPC with admin authorization is needed for atomic saves. No remote schema changes were made.

Image upload and database save are also separate: failed saves or replaced/deleted images can leave unused Storage objects. Add storage cleanup with confirmed object ownership. Do not blindly delete an upload after an ambiguous network failure, since the record may have committed.

The signup trigger enforces unique usernames. A duplicate username or trigger failure can block creation before email is sent; inspect Auth/Postgres logs if `Database error saving new user` appears. This is separate from a signup request that succeeds.
